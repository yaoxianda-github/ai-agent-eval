AI Agent 评测平台 · 操作手册

给 Agent 出题、批改、打分、卡口，一页讲明白

本手册写给从没接触过 Agent 评测的初级测试工程师。你不需要懂大模型原理，也不需要会写复杂代码——跟着步骤走，就能完成第一次评测、看懂轨迹回放、接入 CI 质量门禁，并理解每个参数的含义。

适用：ai-agent-eval 工作台 版本：V2.5 23 任务 · 3 后端 前置：Python 3.9+ 环境 耗时：约 15 分钟上手
一句话理解这个平台

评测平台 = 给每个 AI Agent「出一套题」，让它在干净的工作目录里完成，再按「批改清单」逐条核对产物，给出带证据的得分报告；更进一步，把这套评测接入 GitHub CI，核心任务不达标就自动阻断代码合并。

01

评测平台是什么

先建立整体概念，再动手。这一节回答三个问题：评测的完整流程、五个关键概念、零基础最常见的顾虑。

五个必须理解的概念

任务 Task

一套「考题」

包含给 Agent 的指令（description）、初始文件（fixtures）、批改清单（checkpoints）和分值权重。任务都放在 tasks/ 目录，当前共 23 个。

后端 Agent

一个「考生」

被测的 AI 助手。平台内置三个后端：minimal-react（自研白盒基线）、deepseek-harness（DeepSeek 官方黑盒）、aider（第三方黑盒）。同一套题可让多个考生各做一遍横向对比。

校验点 Checkpoint

批改清单的一条

一条可自动执行的判定规则，例如「文件 answer.txt 存在」「内容包含 36」。全部通过 = 任务通过。共 5 种确定性类型 + LLM 语义判分。

轨迹 Traces

Agent 的「思考过程」

运行详情页以时间线展示全链路：输入意图 → 知识检索 → 模型生成 → 工具执行。黑盒后端（dsh）也能通过 session 解析还原模型 reasoning 与工具决策。

门禁 Gate

上线的「拦路虎」

把评测接入 GitHub CI：core 任务包通过率不达标，退出码非 0，分支保护 required check 直接阻断合并。让 Agent 能力成为硬卡口，不是软参考。

成本 Cost

花了多少钱

双口径：任务选择时看「预计成本」（token 模型估算），运行后看「实际成本」（DeepSeek 余额差分，精度 ¥0.09）。工作台与 CI 报告均展示。

零基础最常见的问题

会不会很复杂？我需要先学大模型知识吗？

不需要。平台把「评测」抽象成了「出题 + 批改 + 看轨迹」。你只需要：选一个任务 → 点运行 → 看结果和轨迹。背后的模型调用、沙箱隔离、判分逻辑、CI 集成都由框架处理。

我需要写代码吗？

只是使用：完全不用。工作台全程浏览器操作。如果你以后想自己「出题」（新增任务），只需要填一张表单，平台会自动生成配置文件。CI 门禁只需在 GitHub 仓库加一个 workflow 文件。

跑一次评测会花很多钱吗？

成本可控：默认模型 deepseek-chat 很便宜；任务管理页每任务有「预计成本」提示；运行后「实际成本」用余额差分精确到 ¥0.09。实测 core 门禁 12 任务 × 3 采样 = 36 次运行，总成本仅 ¥0.06。第一次体验建议先跑 1 次。

结果靠谱吗？会不会是 Agent「自报成绩」？

不会。判定完全看产物，不看 Agent 自己怎么说——校验点检查的是真实生成的文件内容和命令执行结果。多 run 采样会给出 best / mean / std / pass_rate，把「运气」也暴露出来。轨迹回放让你能看到 Agent 每一步在做什么。

黑盒后端（如 deepseek-harness）能看到模型思考过程吗？

可以。V2.4 起，deepseek-harness 运行结束后会解析其隔离 DSH_HOME 下的 session.jsonl.zstd，提取模型 reasoning、工具决策、最终输出（llm 节点）与工具执行（tool 节点），在轨迹回放时间线里完整呈现——黑盒不再「黑」。

02

安装与启动

环境准备好后，三步即可打开工作台。以下命令均在终端执行（macOS 的 Terminal / Windows 的 CMD 或 PowerShell）。

第 1 步：安装框架

# 进入项目目录（macOS 示例） cd ~/Desktop/yaoxianda/doubaowork/ai-agent-eval # 安装开发依赖 + Web 工作台依赖 pip install -e ".[dev]" pip install -e ".[web]"

第一次安装会自动装上 FastAPI、uvicorn 等依赖。若提示失败，确认 Python 版本 ≥ 3.9（命令行执行 python --version 可查看）。

使用 deepseek-harness 后端：需额外安装 Node.js ≥ 22（dsh 运行时依赖）。dsh 会使用评测专用隔离目录 ~/.cache/agent-eval/dsh-home，凭据只来自环境变量 DEEPSEEK_API_KEY，不会读取你个人的 ~/.dsh/ 配置（避免旧凭据导致 403）。

第 2 步：配置 LLM API Key

评测需要调用大模型让 Agent 干活。平台默认使用 DeepSeek，需要你准备一个 API Key。配置后请重开终端再继续。

# macOS / Linux（写入 ~/.zshrc 或 ~/.bashrc 永久生效） echo 'export DEEPSEEK_API_KEY="sk-你的密钥"' >> ~/.zshrc source ~/.zshrc # Windows（写入用户环境变量，永久生效） setx DEEPSEEK_API_KEY "sk-你的密钥"
没有 Key 也能安装和打开工作台，但「运行评测」会因缺少密钥而失败。平台会如实报错，不会假装成功。

第 3 步：启动工作台

在终端执行：

agent-eval workbench

看到如下输出后，用浏览器打开 http://127.0.0.1:8000 就进入工作台了。

Web 评测工作台启动中: http://127.0.0.1:8000 （Ctrl+C 停止）
后台运行（推荐）：macOS/Linux 可用 nohup agent-eval workbench > /tmp/workbench.log 2>&1 & 后台启动，关掉终端不中断。端口被占用时先释放：lsof -ti tcp:8000 | xargs kill -9（macOS），再重启。也可换端口：agent-eval workbench --port 8080。

04

表单参数详解

这是本手册的重点。「工作台」视图里的每个输入框、下拉框都对应一次评测的关键设置。下面逐个解释：它是什么、怎么选、新手建议。

运行控制台：5 个参数

参数是什么可选值新手建议
任务 要执行的考题（Task），决定 Agent 要完成什么、按什么清单批改。 任务列表，来自 tasks/（当前 23 个，覆盖 L1-L5，含 RAG 检索任务 T701/T702） 第一次选 T001，简单直观、费用低；想体验检索选 T701。
后端 被测的 Agent（考生）。不同后端能力与风格不同。 minimal-react（自研白盒基线，轨迹最完整）· deepseek-harness（DeepSeek 官方黑盒，可还原模型层）· aider（第三方黑盒） 默认 minimal-react 即可。对比官方 Agent 能力选 deepseek-harness。
模型 驱动 Agent 的底层大模型名。 默认 deepseek-chat，可换成你 Key 支持的其它模型 保持默认。换模型会改变行为，是评测的「自变量」之一。
超时（秒） 单个 Agent 本次运行的最长时长，超过即强制停止，判为未完成。 覆盖任务默认值（通常 300，T502 为 600，T601 为 120） 不填就用任务默认。任务卡住时，这是兜底保护。
采样次数 同一任务重复运行的次数（runs，1–20）。Agent 有随机性，跑多次才能看出稳定性。 1 – 20，默认 1 体验用 1；正式对比建议 3，可看到 best / mean / std / pass_rate。

预计成本提示

任务选择后，工作台会显示该任务的「预计成本」（基于 token 成本模型估算：prompt ¥1/1M、completion ¥2/1M）。列右上角有感叹号，鼠标悬浮或点击可查看成本计算逻辑。无数据时显示「--」并附说明。

命令行等价参数

如果你偏好命令行，同一套设置用 agent-eval run 完成，参数一一对应：

# 完整参数示例 agent-eval run --task T001 --agent minimal-react --model deepseek-chat --timeout 300 --runs 3 # 常用组合：跑 3 次采样看统计 agent-eval run --task T701 --agent minimal-react --runs 3 # 输出示例： # 统计 (N=3): best=1.0 mean=1.0 std=0.0 pass_rate=1.0

这些参数背后的设计意图

为什么要采样

对抗非确定性

同一个 Agent 跑同一道题，结果可能不同。单次成绩可能是「运气」。多跑几次，best 看能力上限、mean 看平均水平、std 看稳定性、pass_rate 看通过率。

为什么要超时

防止失控拖垮评测

Agent 可能陷入死循环或长时间空转。超时会强制终止该次运行并记录，不会阻塞整批任务。

后端 vs 模型

两个不同的「变量」

后端是 Agent 的思考与工具框架，模型是底层的语言能力。评测时可以固定一个、只改另一个，才能得出可信对比。

成本透明

评测不是烧钱

任务选择时看预计成本，运行后看实际成本（余额差分）。采样次数、模型选择共同控制花费。建议先小步验证，再放大采样。

5 种确定性校验点 + LLM 语义判分

校验点是任务的核心。它决定「什么算做对了」。

类型判定逻辑（通过条件）需要填写的字段
file_exists某个文件 / 目录存在path
file_not_exists某个文件 / 目录不存在path
content_contains文件内容匹配指定正则path + pattern
content_not_contains文件内容不包含指定正则path + pattern
cmd_exit_zero执行命令退出码为 0cmd
llm_judgeLLM 按 rubric 语义判分（开放任务）rubric（可选）
约定：path 相对 Agent 的工作目录；cmd 中的 @scripts/xxx.py 会被替换成项目 scripts/ 的绝对路径——把复核脚本放仓库里，避免被 Agent 篡改。

RAG 检索任务怎么设计

V2.4 起，工具集新增 search_kb（BM25 检索），Agent 可在任务的 kb/ 知识库中做关键词检索。设计 RAG 任务时：

知识库

多文档 + 干扰项

在 fixtures/kb/ 放多份 Markdown 文档，其中包含干扰信息（如其他产品也标类似数字），逼 Agent 用完整查询而非单关键词检索。

校验点

产物 + 内容双重校验

用 file_exists 检查答案文件存在，用 content_contains 检查答案包含正确内容。T701 要求答案只含数字（如 36），T702 要求两段信息归纳。

一个完整例子：T701 RAG 检索

# tasks/T701/spec.yaml（节选） id: T701 level: L2 title: 知识库检索-质保查询 description: | 在 kb/ 知识库中检索云帆服务器 FS-200 的整机质保月数， 将答案（只含数字）写入 answer.txt fixtures: kb/ checkpoints: - id: c1 verifier: file_exists target: answer.txt weight: 0.4 - id: c2 verifier: content_contains target: answer.txt expect: "36" weight: 0.6

T701 的知识库里有 5 份文档，其中「内部通知」里其他产品（X2）也标了 36 个月——Agent 必须用完整查询「云帆服务器 FS-200 整机质保」才能命中正确文档，单搜「质保」会被干扰项误导。这就是 RAG 评测的设计巧思。

轨迹回放：全链路时间线

运行详情页的「轨迹回放」面板，按时间顺序（绝对时间 + 相对首节点耗时）展示一次评测的完整链路，四类节点用不同颜色区分：

输入意图
任务描述（intent 节点），标记为「开始」
知识 / 检索
search_kb BM25 命中、read_file、list_dir 返回的知识片段
模型生成
每步 LLM 输出：minimal-react 记录 model/tokens；dsh 解析出 reasoning/工具决策/final
工具执行
工具调用与观察结果：write_file、run_command 等

支持按类型过滤（全部 / 意图 / 知识 / 模型 / 工具）与长文本展开/收起。时间显示为「HH:MM:SS +Xs」（绝对时间 + 相对首节点耗时），看模型思考与工具执行的节奏一目了然。

黑盒后端也能看到模型层

deepseek-harness 的轨迹还原：V2.4 起，dsh 运行结束后会解析隔离 DSH_HOME 下的 session.jsonl.zstd（zstandard 模块 → zstd CLI 回退），提取模型 reasoning、工具决策、最终输出（llm 节点）与工具执行（tool 节点）。实测 dsh T001 还原 54 条 traces（intent 1 + llm 36 + retrieval 7 + tool 10），黑盒后端不再只有单步调用记录。

如何阅读运行详情

判定结果 verdict

逐条 PASS / FAIL

每条校验点对应一条判定，带通过状态与说明。所有校验点通过 = 任务通过。

轨迹回放 traces

Agent 做了什么、想了什么

全链路时间线：输入意图 → 知识检索 → 模型生成 → 工具执行。白盒后端记录完整，黑盒后端（dsh）通过 session 解析还原模型层。

产物预览

看真实文件

工作目录里的产物文件可在线预览。仅支持常见文本类型且 ≤ 200KB，并做了路径穿越防护，安全浏览。

采样统计 + 成本

多次运行怎么看 + 花了多少

N 采样数 · best 最高分 · mean 平均分 · std 标准差 · pass_rate 通过率。实际成本用 DeepSeek 余额差分计算。

一键生成分享报告

在「报告」视图点击生成，或命令行执行 agent-eval report，会聚合全部运行记录，产出一个自包含的 HTML 报告（reports/report.html），离线也能打开，适合发给同事或放在评审里。

PASS / FAIL
放行合并 or 退出码非0阻断

agent-eval ci 命令

# 跑 core 门禁（12 任务 × 3 采样） agent-eval ci --gate core --agent minimal-react \ --junit-xml results/junit.xml \ --allure-dir results/allure-results # 多 Agent 横向对比（每 Agent 独立跑，全部达标才 PASS） agent-eval ci --gate core --agent minimal-react --agent deepseek-harness # 输出： # JUnit XML（每任务一个 suite，CI 直接解析） # Allure results（标准测试报告可视化） # ci-report.json（agent × task 结果矩阵 + 成本） # 门禁未通过时退出码非 0（阻断合并）

gate.yaml 配置

# ci/gate.yaml gate: core: # 上线卡口：PR 合并前必须通过 tasks: [T001, T102, T103, T207, T305, T306, T308, T303, T401, T402, T701, T702] runs: 3 # 多采样对抗 LLM 非确定性 task_pass_ratio: 0.5 # 任务级多数制：3 run 中 ≥2 通过才算该任务通过 min_pass_rate: 0.9 # 12 任务允许 1 个未通过 full: # 全量回归：合并后/发布前 tasks: "*" # 全部 23 任务 runs: 1 min_pass_rate: 0.8

门禁判定语义

第 1 层

任务级多数制

每个任务跑 runs 次 → 任务通过 = 通过 run 数 / runs ≥ task_pass_ratio。3 次中至少 2 次通过才算该任务通过，对抗单次运气。

第 2 层

门禁通过率

gate 通过率 = 通过任务数 / 总任务数 ≥ min_pass_rate → PASS；否则退出码非 0。core 包 12 任务 × 0.9 = 允许 1 个未通过。

在 GitHub 仓库启用

# .github/workflows/agent-eval-gate.yml（骨架） - run: pip install "git+https://github.com/yaoxianda-github/ai-agent-eval.git" - run: agent-eval ci --gate core --agent deepseek-harness \ --junit-xml results/junit.xml --allure-dir results/allure-results - if: failure() uses: actions/upload-artifact@v4 with: { name: reports, path: "results/*" }

配合分支保护：GitHub 仓库 Settings → Branches → 添加 required check（如 agent-eval core gate）→ 失败即禁止合并。

实测数据：core 门禁 12 任务 × 3 采样 = 36 次运行，耗时 251 秒，token 248,722，成本仅 ¥0.06，通过率 0.917（11/12，T207 老任务波动）≥ 0.9 → PASS。端到端验证见演示仓库 agent-eval-demo（PR 阻断 → 修复 → 放行完整链路）。
08

成本核算：预计与实际双口径

用户在选择任务时即可预知成本，运行后得到真实花费——评测不再是黑盒开销。

预计成本（事前）

token 成本模型估算

基于任务预期 token 用量估算：prompt ¥1 / 1M tokens、completion ¥2 / 1M tokens。展示位置：任务管理页每任务成本列。列右上角感叹号悬浮/点击可查看计算逻辑。无数据时显示「--」并附说明。

实际成本（事后）

DeepSeek 余额差分

运行前后调用 DeepSeek /user/balance 接口做差分（curl 实现，兼容 urllib SSL 失效），批量差分精度 ¥0.09。黑盒后端 token=0 时兜底不报错。展示位置：运行历史实际成本列 + CI 报告 ci-report.json。

为什么用余额差分而不是 token 估算

黑盒后端（deepseek-harness / aider）不暴露 token 用量，只有余额差分能覆盖所有后端的真实成本。而且余额差分是「真金白银」的花费，比 token 估算更可信（token 估算不包含重试、超时、工具调用的额外开销）。

成本数据在哪看

口径位置说明
预计成本任务管理页（每任务成本列）token 模型估算，选择任务时即可看到
实际成本运行历史页（实际成本列）余额差分，每次运行的真实花费
实际成本运行详情页单次运行的成本明细
批量成本CI 报告 ci-report.json整轮门禁的总成本，含 agent × task 矩阵
成本控制建议：先小步验证（单任务、runs=1），确认任务设计合理后再放大采样（runs=3）。core 门禁 36 次运行仅 ¥0.06，成本可控。换更贵的模型前，先看预计成本评估预算。

常见问题与排障

按「现象 → 原因 → 处理」整理最常见的问题。更详细日志可查看结果目录下的 run.json。

现象可能原因处理
运行报「缺少 LLM API Key」 未配置 DEEPSEEK_API_KEY macOS：echo 'export DEEPSEEK_API_KEY="sk-..."' >> ~/.zshrc && source ~/.zshrc；Windows：setx DEEPSEEK_API_KEY "sk-..."，重开终端再启动工作台。
deepseek-harness 报 403 / 预扣失败 使用了 ~/.dsh 个人旧凭据 平台使用隔离 DSH_HOME（~/.cache/agent-eval/dsh-home），凭据只来自环境变量。确认 DEEPSEEK_API_KEY 有效且未过期。不要手动配置 ~/.dsh。
运行报「未知后端」 后端名称拼写错误或未安装 在下拉框里选存在的后端；aider 需额外 pip install -e ".[aider]"；deepseek-harness 需 Node ≥ 22。
运行报「未知任务」 任务 ID 不存在于任务清单 在任务管理确认；任务目录需在 tasks/ 且在 manifest.yaml 中登记。
8000 端口被占用 / 地址已在使用 已有进程监听该端口 macOS 释放端口：lsof -ti tcp:8000 | xargs kill -9，再重启工作台。或换端口：agent-eval workbench --port 8080。
工作台刷新后报「not found」 SPA 路由刷新问题 从首页（http://127.0.0.1:8000/）重新进入，通过左侧导航切换页面，不要直接刷新子路由。
运行详情执行轨迹显示乱码 命令输出编码非 UTF-8（如 GBK） V2.x 已修复：命令沙箱做输出编码探测，GBK 自动转 UTF-8。升级到最新版本即可。
产物文件读取报 500 路径穿越或相对/绝对路径混用 V2.x 已修复：产物预览相对 results_dir 做路径安全校验。升级到最新版本即可。
任务管理预计成本显示「--」 该任务无成本估算数据 属正常现象。部分任务（如 llm_judge 开放任务）成本模型暂未覆盖，显示「--」并附说明。运行后可看实际成本。
结果一直 pending / running Agent 卡住或任务耗时长 等待超时强杀（任务默认超时）；或检查网络 / Key 是否有效。dsh 后端首次运行需下载依赖，可能较慢。
多次运行结果不稳定 Agent 本身有随机性 属正常现象。加大采样次数（runs）看 best / mean / std / pass_rate，不要用单次下结论。core 门禁用 task_pass_ratio 0.5 多数制对抗随机性。
CI 门禁失败但本地跑通过 CI 环境与本地不同（模型/Key/网络） 检查 CI 的 DEEPSEEK_API_KEY secret 是否配置；CI 用 deepseek-harness 后端需确认 Node 版本；下载 CI artifact（results/*）查看具体失败任务的 run.json。
结果都存在哪：每次运行的结果在 results/runs/<run_id>/（含 run.json、workspace 工作目录、traces 轨迹数据），SQLite 只是历史索引，原始证据始终是文件。
