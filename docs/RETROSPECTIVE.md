# MVP 复盘（2026-09-02 ~ 09-03）

> 一周从 0 搭起通用 AI Agent 评测框架。这篇复盘回答三件事：**哪些决策值、踩了哪些坑、V2 该先做什么**。

## 一、做对了什么（保持）

1. **任务包即契约（task-spec@v1）**
   任务作者只写 `spec.yaml + fixtures + 判定脚本`，不碰框架代码。这让"加任务"变成纯 YAML 工作，是框架能被他人复用的前提。

2. **后端注册表 + 适配层**
   能同时接入两种风格迥异的 Agent：自研白盒（步骤级轨迹）和第三方黑盒（单次调用）。aider 的适配（`--file` 传输入文件、git baseline、`stdin=DEVNULL`）证明了"适配层隔离差异"这一设计必要且有效。

3. **判定看产物、不看自报**
   max_steps（Agent 没调 finish）但产物全对的 run 照样 4/4——说明"以校验点为准"是正确设计，不受 Agent 表达影响。

4. **对抗非确定性：多 run + 报告取最好 + 保留全部证据**
   LLM Agent 同任务多次运行结果不同是常态，保留证据比只给一个分诚实得多。

5. **判定器失败保留退出码 + stderr**
   这让我们能定位"是 Agent 错还是框架错"，也直接催生了最值得讲的故事（验证验证器）。

6. **全程 git 手动提交 + 进度文档**
   每天一个文档化里程碑（PROGRESS.md），过程可追溯，Demo 有据可讲。

## 二、踩过的坑（教训）

1. **适配第三方工具前先验证参数版本**
   aider 0.70 没有 `--no-color`（应是 `--no-pretty`），直接导致退出码 2。教训：对黑盒 CLI，先用 `--help`/最小命令冒烟，再接入框架。

2. **黑盒 Agent 有任务类型盲区**
   aider 在"改已有代码"类任务通过，在"从零生成数据产物"类任务上陷入"要不要新建文件"循环而超时。教训：**选后端要匹配任务类型**，评测本身会暴露这种适配度——这也是产品价值，不是缺陷。MVP 收窄（T102 记为适配度限制）是合理止损。

3. **LLM 非确定性超出预期**
   T102 对自研基线也是时好时坏（有 3/3 也有 0/3）。教训：单次 run 不能当结论，需要 N 次采样 + 均值/最好/方差口径（V2 必做）。

4. **超时要按任务留余量**
   把 aider 超时从 300s 调到 60s 实验，结果发现 T001 需要 ~55s——超时设置必须基于实测留余量，否则正常任务被误杀。

5. **判定器自己也会错**
   cmd 校验的相对路径在 `cwd=workspace` 下解析错位，导致"Agent 做对、判定误判"。教训：**验证器本身要有单测**（V2 P0）。

6. **依赖冲突与隔离**
   装 aider 时与已有 opencv/selenium 依赖打架。教训：大依赖尽量用虚拟环境 / 项目级 venv 隔离，避免污染全局环境。

7. **环境缺陷会消耗大量时间**
   本会话命令执行通道有基础设施 bug（路径含 `\t` 解析异常），git 全程只能手动跑。教训：开发前先确认工具链可用；也提醒"工具依赖"本身是风险点。

## 三、数据与结论（可下钻）

- T001：minimal-react 多次 4/4；aider 4/4（54.6s）→ **文件改写类任务两后端均可胜任**
- T102：minimal-react 3/3（最好）/ 0/3（失败 run）；aider 超时（0 分）→ **数据生成类任务考验 Agent 自主规划能力，非确定性显著**
- 一次 T001：max_steps 但产物正确 4/4 → **判定与 Agent 收尾解耦**
- 一次 T102：Agent 产物正确但判定误判 FAIL → 框架 bug 被证据链抓到并修复

## 四、V2 路线图（优先级排序）

| 优先级 | 事项 | 原因 |
|---|---|---|
| P0 | 判定器/框架自身单元测试 | "验证验证器"，防止再次出现误判类 bug |
| P0 | Docker / 子进程沙箱隔离 | 当前 `run_command` 用 shell=True，只能在干净目录跑，OS 级隔离是接任意 Agent 的安全底线 |
| P1 | 每任务多 run 采样（N=3/5）+ 均值/方差 | 对抗非确定性，让分数有统计意义 |
| P1 | Langfuse 可观测接入 | 轨迹已结构化，接入成本低，补齐"为什么这么表现"的分析能力 |
| P1 | 更多任务类型 + 后端 | 扩大覆盖面：加代码编辑类任务（aider 强项）、接 Claude Code / OpenHands 等 |
| P1 | LLM-as-a-Judge（T502 预留） | 覆盖主观/开放类任务 |
| P2 | 黑盒桌面端采集（豆包工作 / WorkBuddy） | 有观察价值但工程量大，需 UI 自动化，放后 |
| P2 | 插件注册表 + pip 发布 | 让社区可贡献任务与后端 |

**一句话总结**：MVP 证明了"任务契约 + 后端注册表 + 产物判定"这条路的可行性；最大的收获不是代码量，而是几个**有证据的真实发现**（非确定性、验证验证器、适配度），它们让这个项目在面试和分享里经得起深挖。
