背景与目标

为什么需要一个可复用的 Agent 评测体系

背景

Agent 输出不确定

大模型 Agent 效果好坏常靠人工目测，结论难以横向对比、难以沉淀，也很难在团队内复现。

目标

一套完整评测链路

从任务定义 → 执行 → 判分 → 报告的全流程体系；任务与后端可插拔，结论可复现、可分享。

原则

结论要有证据

判定看产物、不看 Agent 自报；多 run 保留证据；验证器自身也要被验证。

需求提出与打磨

从一个问题，打磨成一套框架

起点不是「做产品」，而是测试工程师的一个日常疑问：怎么给 Agent 的能力一个客观、可复现的答案。
第一版问题
能不能跑起来
让一个 Agent 真正去执行任务，而不是只聊天。
打磨 v1
结论要可复现
任务包即契约 + 多后端 + 多 run 采样，结论可对比、可追溯。
打磨 v2
要能常用
浏览器全程操作的工作台 + 一键启动，降低使用门槛。
打磨 v3
开放任务也要判分
LLM-as-a-Judge 语义判分，周报这类开放产物也能量化。
明确不做

不做通用 Agent 平台，只做评测

不接在线 SaaS、不做鉴权多用户、不碰桌面端采集——本地优先，专注把「评测」这件事做扎实。

MVP · 经验

一周跑出的五个关键结论

1

Agent 是非确定性的

同一任务多次运行结果不同 → 多 run 保留证据，报告取最好成绩。

2

判定看产物，不看自报

max_steps 未收尾但产物正确，照样得分——以产物为准绳。

3

验证器也要被验证

判定器自身出过路径 bug，靠完整证据链反查定位。

4

没有银弹

aider 擅长改已有代码，在「从零生成数据产物」任务上循环超时。

5

接口差异用适配层隔离

后端适配层注册表，让引擎与具体 Agent 解耦。

V2.1 · 实战

四类缺陷，逐个修复

Python 3.9 类型兼容

str | None 运行时崩溃

PEP 604 是 3.10+ 语法，FastAPI 路由参数运行时求值直接崩 → 改用 Optional[str]。

SQLite 跨线程

后台线程写入、API 线程读取冲突

SQLite 对象不能跨线程使用 → check_same_thread=False + 线程锁保护。

run_id 不一致

run 404：自生成与预生成对不上

run_one 内部自生成 run_id，与 Web 预生成不一致 → 增加可选 run_id 参数注入。

前端白屏

app.js 一处引号不配对

字符串引号未闭合导致整个脚本语法错误、页面空白 → 修复后 56 用例全绿。

经验沉淀

四条可复用的经验

架构

引擎复用优先

新形态先包一层，不推翻内核——工作台对 CLI 引擎 100% 复用、零重写。

可靠性

诚实降级

外部依赖缺失时静默降级，不假报成功；判分器无产物时如实返回，不硬编。

验证

证据链思维

判定器自身出过 bug，靠完整证据链定位；独立复核脚本让结论可交叉验证。

扩展

插拔式后端

适配层注册表隔离接口差异，白盒 / 黑盒 Agent 共用同一套评测链路。

把不可控的 Agent 输出，变成可复现、可分享的评测证据

这正是这个框架想解决的问题，也是它持续演进的方向。
